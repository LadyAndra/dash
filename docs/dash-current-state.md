## Where sync diverges from the original proposal

The architecture proposal (`dash-architecture-proposal.md`) specified iCloud Drive as the canonical data store, with automatic sync on Mac and manual export/import on iOS. **This was superseded.** Once Android/e-ink entry was on the table, iCloud's lack of Android support made it a dead end.

**What's actually built:** Dropbox OAuth 2 PKCE sync, with auto-renewing refresh tokens. This works automatically on both Mac and iPhone — better coverage than the original iOS plan, and it's what makes a future Android/e-ink device straightforward to add. Manual token expiration (the ~4-hour problem with plain Dropbox tokens) was solved via the PKCE refresh flow.

Everything else in the proposal's data model (Items, registries, content-addressed assets, theme tokens, view-layer architecture) still holds as designed.

- **Project milestones + the stage chip** (August 1, 2026) — Phase M1 of `dash-milestones-calendar-addendum.md`. `formatVersion` is now **2**. Projects carry an optional `milestones` array of `mid`-keyed sub-records (`label` / `date` / `remind` / `done` / `order` / `removed` / `created`); a new `"ms"` op kind with three actions (`add` / `set` / `remove`) carries them through the log. The editor lives on the Project detail page — `js/views/milestone-editor.js` — with add, rename, due date, reminder, drag + ↑↓ reorder, done toggle, and remove-with-restore. `js/milestones.js` holds the pure rules (ordering, date-only comparison, `stageOf`) and imports nothing, so it tests headlessly with no stubbing at all. The stage chip renders in the project header, the projects list, and on rows/cards in list and board; ember only when overdue. **Deliberately not built:** the Today panel (M2) and the Calendar view (M3). See `docs/changes-2026-08-01-milestones.md`
  - **`date` and `remind` on milestones are date-only strings, not timestamps**, unlike `dates.due` on ordinary items — and that divergence is the point, not an inconsistency. "Overdue?" is a plain string comparison, which sidesteps a whole class of timezone and DST bugs where "Aug 15" written on one device renders as the 14th on another. `todayISO()` reads the local calendar fields directly and never touches `toISOString()`. Both 2026 DST switches are covered by tests; don't "tidy" these into Date objects
  - **A reorder is one `set` op on one milestone's `order` field, never a renumber.** Fractional ordering (first = 1000, appends +1000, inserts split the gap) is what lets a reorder on one device and a label edit on another merge without touching each other. Ties from two devices inserting into the same gap break by `mid`, so both converge with no coordination. Whole-list renumbering survives only as a precision-exhaustion repair (~50 consecutive splits into one gap), and there is a test proving it fires
  - **Entries attach to a phase through a link, not through a list on the milestone** (added August 1, 2026, at Andra's request — the addendum §2.2 had said milestones can't have things attached, and she raised it). The link is `{ target: <projectId>, label: "phase:<mid>" }` on the *entry*. `links` is already a set field with add/remove op semantics, so this needed **no new op kind, no new merge rule and no format bump** — there is a test asserting the only op kinds involved are ones that already existed. The relationship lives in exactly one place (the entry's links), so nothing can drift out of step. A milestone row on the project page opens to show what's on it; `store.milestoneMembership(projectId)` builds the whole mid→entries map in **one** archive pass and the editor calls it once per render
  - **An entry can be on more than one phase, by design, because set-merge leaves no alternative.** Two devices assigning the same entry to different phases while offline both survive; "only one phase" can't be enforced without inventing a conflict the model says isn't there. Allowing it openly beats having it happen by surprise. Taking an entry off a phase deliberately does **not** take it out of the project — those are different actions, and collapsing them would silently lose an assignment
  - **The stored `milestones` array is kept sorted by `mid`, not by `order`.** Display order comes from `sortMilestones()`; the array's own arrangement exists only to give the snapshot one canonical form, so two devices that received the same ops in different sequences produce byte-identical files. Secondary benefit: the snapshot stops churning in Dropbox for no reason

- **Colour as ground, and colour you choose** (August 1, 2026) — `changes-2026-08-01-projects-and-colour.md` and `changes-2026-08-01-colour-pickers.md`. The tokens.css rule was amended: the seven palette colours may now be **filled grounds** with ink on top, not only thin marks. Ember is not in the palette and is not part of this — it stays an indicator meaning "past its date" and nothing else, so a plum project block and an ember overdue block can share a page and still say different things
  - **No new colour tokens were needed.** All seven palette values were measured as backgrounds against `--text-on-accent` before the rule was changed: worst pair 5.32:1, best 7.62:1, in *both* themes. Because that ink token flips per theme, a ground survives a re-theme with no second set of tokens to maintain
  - **New scalar field `color` on every item** (nullable; null = inherit the type's colour). This is the **first addition to the data model** in this run of work — everything before it was layout only. It needed one line in `SCALAR_FIELDS` and one in `emptyItem`; LWW, merge and sync were untouched, and `_applyOp` doesn't validate field names so an older device applies a `set color` op harmlessly and just doesn't draw it. The value is a palette *name* or a literal hex — `colorToken()` handles both, so types and statuses keep re-theming as names while a project can hold an exact value
  - **The picker is the SYSTEM picker.** `js/ui/colorfield.js` wraps `<input type="color">`, which on macOS/iOS opens the full spectrum, sliders and eyedropper, plus a hex box and a reset. A custom gradient canvas was considered and rejected: several hundred lines, worse with a finger, worse with a screen reader, to land somewhere less capable than what the OS already ships
  - **The policy is "exact always, warn me"**, chosen by Andra over auto-adjustment. A picked colour is used verbatim; Dash never quietly darkens it. Instead the picker shows two live readings — *as small text* (the colour on the paper ground, the one that bites) and *as a block* — and flags anything under 4.5:1 in plain words, then defers. **The one thing Dash still decides on its own** is which of its two inks goes *on* the colour; that changes the writing, never the colour, and without it a pale pick would produce a block with invisible text and no way out
  - **Custom accent in Settings.** Replaces ember everywhere it appears (~20 places) by writing `--ember`, `--accent-2` and `--ember-ink` into the *existing* `dash.theme` localStorage object that `loadSavedTheme()` already restores — no new storage key, no new startup path. This is the first working slice of the in-app theme editor
  - **`--ember-ink` and `--ground-ink` / `--ground-bg` are the mechanism.** A colour block sets `--ground-ink` (and `--ground-bg`) on itself inline, computed by `inkFor()`; every rule that puts text or a control on a block reads those. That is what lets an **arbitrary hex** — one no stylesheet could have anticipated — stay legible, and what lets the banner's buttons flip their lettering when the project colour changes. All the contrast maths lives in `js/theme.js` (`luminance`, `contrast`, `inkFor`, `colorReport`) so there is exactly one definition of "is this readable" in the app

- **The spatial parameters** (August 1, 2026) — `changes-2026-08-01-spacing.md`. Prompted by "checkboxes and buttons seem oversized sometimes, and a lot of text gets cut off, especially on my phone." Three separate causes, only one of which looked like spacing
  - **`--tap-min` was applied unconditionally in ~28 places.** Correct on a phone; on a desktop with a mouse it isn't an accessibility requirement and it was costing ~132px of every milestone row before a character was drawn — which is *why* labels clipped. Now `--tap-min` (44px) is the untouchable touch floor and `--control-min` is what controls actually use, dropping to **28px** under `@media (pointer: fine)`. Text buttons barely move (padding and label already exceed 28px); what shrinks is the square stuff — tick boxes, ↑ ↓ ✕, icon buttons
  - **The panel grid was optimising for density.** `minmax(320px, 1fr)` means "fit as many 320px columns as possible", which on a 1700px screen produced three cramped ~380px columns — a bigger screen made things *worse*. Now `minmax(--panel-min, --panel-max)`: fewer, wider columns. Measured result on that screen: two columns at the full 660px on a project page, 522px on Home
  - **Four layout tokens** now carry the app's density: `--page-max` (1500px), `--panel-min` (480px), `--panel-max` (660px), `--rail-w` (340px, **Home only**). Making everything roomier is one number
  - **Text clipping had three distinct causes**, and the audit is worth keeping: a long unbroken word overflowing (fixed with `overflow-wrap` on things carrying real names); a control squeezing a field to nothing because a flex item's default minimum size is its *content*, not zero (fixed with `min-width: 0`); and a deliberate two-line preview clamp, which stays. Search had been pinned to 160px on phones — about four characters of your own query
- **Merge notes, small version** (August 1, 2026) — `js/merge-notes.js`. `store.collisions()` had been a stub returning `[]` since the beginning, with the real UI parked in Phase 4; the M1 two-device test was unverifiable without something to look at. Same-field last-writer-wins losers are now recorded (milestones and ordinary fields alike), a "⚠ Merge notes" topbar button appears **only when the list is non-empty**, and each note offers a one-tap restore that writes the losing value back as an ordinary fresh edit. Notes are per-device `localStorage` (`dash.mergeNotes`), never synced — a device that wasn't there has nothing to be told about
  - **Known and documented limitation, not a bug to "fix" later without thought:** a note is recorded only when an incoming op *loses* the race. That rule has zero false positives (an ordinary sequential edit always carries the later stamp, so it always wins), but it means a two-device collision surfaces on one device, not both. Detecting concurrency properly needs vector clocks; Dash chose a scalar hybrid clock deliberately. Recording every cross-device overwrite instead was considered and rejected — it fires on every normal edit-here-then-edit-there and would make the feature noise

- **The code-health pass** (August 1, 2026) — a structural review of every file in `js/`, `css/` and the root before starting M3, written up in `docs/review-2026-08-01-code-health.md`, followed by thirteen cleanups plus one bug found along the way. The review's own verdict is worth keeping: **the architecture was in good shape and unusually faithful to its own documentation** — the store never touches the DOM, views genuinely declare their capabilities rather than being named in a list in `app.js`, derived data really is never written back, and the then-current service-worker `SHELL` was completely accurate. What had accumulated was **residue, not rot**: things left behind by features that were shelved or unregistered the same day. The substantive results:
  - **The app was walking the whole archive about 28 times per redraw.** `renderSidebarFilters()` called `store.all()` once for the total, once per type, once per status and once per tag, plus `store.allTags()` — and it did this on Home and Project too, where the index rail isn't on screen, building it in full and then hiding it with CSS. Since a redraw fires on every store change, that included **every keystroke in the item editor**.   - **`js/entries.js` gained the half of the M3 contract that was missing.** The addendum's Unscheduled tray (§6.3) had nothing to read: an undated milestone can't be an *entry*, because an entry has a `start`. Without this, `calendar.js` would have had to read items directly, breaking §6.1 on day one
  - **A real bug: the item editor's Escape listener was never removed** except on the Escape path. Closing with Done, Delete or the backdrop left it attached, so a later Escape re-ran `close()` on a dead editor and threw — surfacing as the red "Something went wrong inside Dash" banner on a keypress with no connection to anything. One orphaned listener also accumulated per editor opened.   - **Two colours were frozen in the code.** `defaultAccentHex()` returned a hardcoded hex under a comment describing an approach never written, so "Reset to ember" would have reset to a colour a re-themed Dash no longer used. It now reads a new **`--ember-default`** token — deliberately not `--ember`, because `setAccent()` writes that inline on `:root` and reading it back hands you the custom accent you're resetting away from. And the project chips in the item editor were hardcoded to the green tint, making every project green whatever colour you'd picked; they now use `groundStyle()` like everything else
  - **The last six literal colours left `app.css`**, replaced by `color-mix()` over tokens. One mattered: the page's dot grain was a fixed warm brown and therefore **invisible on the dark theme**; drawn from `--text-primary` it now inverts. Opacities were recalculated rather than copied, since near-black at 5% is ~1.6× stronger against cream than the brown it replaced. Shadows deliberately kept a *dark* token rather than an ink one — a shadow must stay dark in both themes or it becomes a pale glow
  - **An AA failure found while auditing, not on the original list:** `--ember-soft` — the Delete button's hover — had no dark-theme value and wasn't in `ACCENT_TOKENS`. The hover is now a 10% wash of `--ember` itself, which fixes both by construction: 4.69:1 on paper, 5.17:1 on the mount. 10% specifically because the wash sits *behind* lettering of the same hue, so stronger costs contrast — 14% drops back under the floor
  - **Dead weight removed**, all proven to have zero readers first: five unused imports, `swatch()`, `setDropboxToken()`, two `dash.view` writes, six dead CSS rules, and **eleven dead colour tokens** (`--tint-*` ×7, `--ember-soft`, `--accent-1/3/4`) plus `tintToken()`. **`--accent-2` deliberately stays** — nothing reads it, but `setAccent()` writes it and the proposal §10 names it, so removing it means touching the accent path. Home's capture heading lost its orphaned roman numeral **"I"**, left over from when Home was a run of numbered plates and only plate I survived the panel rebuild
  - **What was deliberately NOT removed:** the commented-out imports for the pet widgets and for Kanban / Columns. ## The Desk (Phase D1, August 14 2026)

**A project page is the desk.** No toggle, no second face: the banner sits on top, three Peek drawers hang off its bottom edge, and everything below is a bounded surface you arrange by hand. The panels that used to be here have homes — the entry groups became the Filed drawer, the milestone editor moved into its own drawer (mount point only; its focus bookkeeping is untouched).

### What's built

- **Place, move, raise, expand, un-place, restore.** Drag a row out of the Unplaced drawer onto the desk; drag cards around; a tap brings a card to the top; double-click expands it in place into the full entry and again collapses it; drag a card onto the Unplaced handle (or use *Return to tray* on an expanded card) to take it off. Un-placing keeps the position, so putting it back puts it back where it was.
- **Drag empty desk to pan.** The surface is 4400 × 2900 — bigger than the frame on purpose, sized for ~100 entries with room left over.
- **Hold `Z`, or hold the ✧ in the banner, to glance.** The whole desk scales to fit what's actually placed, centred; let go and you're exactly where you were. No zoom state is kept anywhere.
- **Three mini-drawers**, each opening under its own handle at that handle's width, only as tall as its contents need, painted in the project's colour and sliding *over* the desk — opening one never moves a placement. Clicking away closes it, and that click does nothing else.
- **The phone gets Peek as the page**: no desk, no Unplaced shelf (nothing to be unplaced from), milestones as a section.

### The data (desk addendum §12.1)

Desk position is `item.viewState["desk:<projectId>"] = { pos, z, clip, removed, created }`, carried by the new **`"vs"` op** with per-field last-writer-wins. Because the key namespaces the project, the same entry can sit placed on one project's desk and unplaced on another's at the same time, and the two never contest.

Milestones and desk placements are now **the same merge code** — one shared sub-record engine both op kinds call, keyed exactly as Phase M1 keyed it, so existing logs and snapshots merge byte-identically to before.

`formatVersion` is **3**. It marks the desk format *family*: the later phases' `"dk"` and `"hl"` op kinds are covered by the same 3 deliberately, and ignore-and-preserve makes a device that's behind safe regardless.

### Fixed in the first deploy (same day)

The drawers didn't open: the drawer body was appended to the page instead of left inside the handle row, so its `top: 100%` resolved against the whole page and it opened below the fold. The desk also shipped as a framed scroll box with native scrollbars instead of the edge-to-edge pannable surface, and the banner's buttons fell back to paper styling because `app.css` scoped its on-a-colour-ground rules to `.project-banner` and the new banner is `.on-ground`. All four fixed; see `changes-2026-08-14-desk-d1-fixes.md`.

**Second round of fixes, same day:** a sync data-loss path (a changed remote snapshot was assigned over live items, eating edits made since it was written — new entry titles reverting to "Untitled"), and one broken rule that produced four separate drag symptoms: the raise-on-touch was writing to the store on pointerdown, re-rendering the desk mid-drag and destroying the captured card. **Nothing may write to the store between pointerdown and pointerup.** Also: an expanded card is now two surfaces (header drags, body selects), the banner's ✧ works, and a desk opens centred on the mat rather than in the corner.

**Post-deploy root-cause pass (steps 1–2 of 5):** the app was **re-syncing with itself** — `flush()` wrote a snapshot but never recorded it in `_lastSnapText`, so the next poll re-downloaded the device's own file and did a full reload + page rebuild every 8–10 seconds. That random rebuild is what killed drags mid-gesture, dropped scroll input and repainted new entries in stages. And the **glance was corrupting the saved scroll position**: it wrote the position back while the surface was still transitioning from its scaled-down size, the browser clamped it to ~0, and every later rebuild "restored" to the corner. The glance took two attempts: restoring the position after the transition still lost the race, so the surface is now wrapped in a **sizer** that owns the scrollable area and is never transformed — the glance is purely a transform and never writes the scroll position at all. **Steps 3 and 4 are done.** `scheduleRender()` in `app.js` now respects a hold, exposed to views as `ctx.holdRenders()`: the desk takes one on pointerdown and releases it on pointerup, pointercancel, window blur and teardown, so **nothing anywhere in the app redraws while a pointer gesture is in progress** — the desk's existing "no writes during a drag" rule only ever covered its own writes, and a sync pull or an editor keystroke could still destroy the captured card. And the double-click memory moved from `wireDesk`'s closure into `viewLocal`, because the first click on a lower card commits a raise, which rebuilds the desk, which destroyed the closure holding the memory — so double-click-to-expand only ever worked on a card already on top. **Step 5 turned out not to be needed for the flicker** — see below.

**The typing flicker (August 15, 2026, `dash-v37`).** Typing in the entry editor flashed the whole screen, once per keystroke. Step 5 of the root-cause pass had this down as "rebuild the desk in place instead of from scratch", a medium-sized refactor of `js/views/desk.js`. The actual cause was one frame of timing, and the fix is about twenty lines.

Every store write rebuilds the page, and the editor saves on every keystroke, so the desk was rebuilt once per character — that part was known and is correct for the op-log design. What made it *visible* was that a brand new scroll container starts at (0, 0) and the code putting the scroll position back ran inside `requestAnimationFrame`. A rAF callback fires on the **next** frame, so the browser had already painted a frame of the desk's empty top-left corner before the restore landed. That corner-flash was the flicker.

The desk now hands out a `_deskMount()` hook, and `views/project.js` calls it **synchronously**, in the same task as the `appendChild`. Measuring and scrolling are both valid at that point precisely because the element is already in the document, and nothing paints until the task ends — so the corner is never drawn and there is nothing to flash. A `requestAnimationFrame` fallback stays behind it for any future caller that forgets the hook, guarded by a `mounted` flag so the work happens exactly once.

**Step 5 itself is still available and is still the better end state** — reconciling by card id would take the per-keystroke rebuild cost away entirely and is the natural ground for D2–D4. It is no longer urgent, and it is no longer the flicker's fix. Do not do it as a bug fix; do it as a performance change, on its own, when the desk gets busy enough to need it.

**The first click on the desk highlighted the top of the page (v38).** Mousedown begins a text selection, and the desk carries almost no text of its own — so the browser anchored to the nearest text it could reach, which sits *above* the surface, and swept backwards to get there. "First click" is what named it: a freshly rendered page has its selection anchor at the start of the document, so the first press drew a selection from the top of the document down to the cursor; afterwards the anchor sat inside the desk with nothing above it. Fixed with `user-select: none` on `.desk-viewport`; the expanded card already puts selection back on itself for its body. **It had to be CSS** — `preventDefault()` on pointerdown would also suppress the compatibility mouse events that double-click-to-expand depends on, which is why `wireDesk` has always refused to call it. Any future "stop the browser doing X on the desk" should try a CSS property before preventDefault.

**Two bugs before D2 (August 15, 2026, `dash-v39`).** See `changes-2026-08-15-two-bugs.md`.

*Dismissed merge notes came back after a reload.* Dash kept one record of a merge note — the list on screen — and the key set that `_noteCollision()` checks against was derived from that list and nothing else. So dismissing a note took it off the screen **and** erased the record that it had ever existed, and the next log re-read recreated it from scratch. It only showed up after a reload, because the in-memory key set still held the key within a session; that is how it sat beside a green suite. There is now a second, per-device localStorage record, `dash.mergeNotesResolved`, that nothing shortens. **The general lesson: "currently displayed" and "already dealt with" are two different facts, and a UI list must never be the only home of the second one.**

*Tapping Projects on a fresh open flashed back to Home.* Not a view bug at all. `skipWaiting()` + `clients.claim()` hand an open tab to a new worker the moment it finishes installing, and `index.html` answered that with an unconditional `window.location.reload()`. Installing the ~50-file `SHELL` takes about **two seconds after the page is tappable**, so a tap on Projects inside that window was thrown away by the reload, which then landed on Home (the fixed cold-start view). The scoped fix — check for a waiting worker early in boot — was measured and **ruled out**: at 30ms there is no waiting worker and none installing, because the new worker is only fetched at `window.load`. The reload is now conditional on nobody having touched the page yet; otherwise it waits for the tab to be hidden.

**The editor closing on a drag-to-select (same round).** Pre-existing, not desk-specific. A `click` fires on the nearest common ancestor of pointerdown and pointerup — so starting a text selection inside the modal and releasing a few pixels past its edge made the browser report a click on the scrim, and the backdrop handler shut the editor mid-select. The scrim now requires **both** ends of the gesture to be the scrim itself. The two smaller scrims in `editor.js` (the inline project creator and the link picker) still have the old single-ended check; they are search-and-name boxes rather than long text, so it bites far less there, but the same three-line pattern fixes them if it ever becomes annoying.

**The lesson worth keeping: jsdom has no layout.** The render tests check structure and data and are worth having; they cannot see position, size or overflow, and must never be trusted to. Anything geometric is checked by looking at it.

### Rules this code must keep

- **One archive pass per render.** `deskData()` in `js/desk.js` is the only thing that walks `store.all()`; the drawers read the same result. Test-enforced.
- **Drags commit on drop, never per frame.** Pointer-move is local state; nothing writes — and therefore nothing re-renders — until release, so a sync landing mid-drag can't steal the card.
- **Positions clamp in the model, not just on screen.** Clamping only at draw time leaves a stored position off the edge, which reads as a stuck card.
- **A raise only writes when the card isn't already on top**, or every idle tap would append an op.
- **The desk viewport owns its stacking context** (`z-index: 0; isolation: isolate`). Without it, card z-indices compete with the banner and drawer at page level and a recently-touched card paints over an open drawer.
- **`viewState` is excluded from create-skeleton filling** in `fillCreateBlanks`, exactly as `milestones` is. Without that, a create op arriving after a placement op wipes the placement — see the D1 change note.
- **Desk arrangement is pointer-only, and that is honest only because Peek exists.** Nothing may ever live as an arrangement alone.

## Clips and post-its (Phase D2, August 16 2026)

### What's built

- **Clip cards together.** The clip mark in the banner turns the desk into a picking mode: click the cards you want, press it again, and two or more become one clip. One card cancels; nothing is written on the cancel path. Escape cancels too.
- **A closed clip is one object.** Members draw as a tight sheaf, each still at its own angle, with the paperclip mark on the corner of the top card. Dragging any part of it moves the whole cluster and writes one ordinary position op per member on drop. A tap raises every member.
- **Double-click the mark to open it.** Members lay out in a reading grid, flat, and can be double-clicked individually to expand as usual. Double-click the mark again to close.
- **Two ways to unclip.** Right-click the mark for a small menu with *Unclip* (the whole thing), or — only while it's open — drag one card out of the grid, which unclips that card and gives it the position it lands at. The gesture only exists in one state, which is what stops it being confused with a cluster drag.
- **Post-its.** Double-click bare desk to make one. Text in place, no title, no status. Drag it onto a clip to attach it — it stays exactly where it is dropped and rides the stack from there; drag it back onto open desk to detach. Emptying the text of one that had words throws it away; a blank one you never typed into is thrown away by **Escape**, and right-click always offers *Throw this away*.

### The data (desk addendum §12.2–§12.3)

Project-side desk objects live on the **project item**, in an optional `deskObjects` field, carried by the new **`"dk"` op** addressed by `(projectId, coll, id)`. Two collections this phase: `clip` (`{ cid, created, removed }` — nearly empty, wordless by data shape) and `note` (`{ nid, text, pos, clip, offset, created, removed }`). Both arrays are kept sorted by id, so two devices receiving the same ops in different order write byte-identical snapshots.

**A post-it has two placements and never both at once:** `pos` while it is free on the desk, `offset` `{dx, dy}` from its clip's derived anchor while it is attached. `offset` was added in round 2 (August 16) rather than overloading `pos`, mirroring the wonder-symbol pattern §12.3 already specifies — before it, an attached note ignored position entirely and drew at the clip's derived bounds, which made it the one object on the desk where dropping it somewhere was not the decision. Absence still means "none": a note written by the first D2 build has no `offset` and gets one default placement until it is next dragged. No migration, no version bump.

**Clip membership is not on the clip.** It is a `clip` field on each card's existing `desk:<projectId>` viewState record — the same `"vs"` op D1 built. A card is therefore in at most one clip per desk, enforced by the shape rather than by a rule.

**A clip stores no position and no member list.** Where it sits is derived from its members every render (the anchor is the topmost member's position), which is exactly why dragging one is a loop of ordinary card moves and why unclipping repositions nobody — everyone is already where the last cluster drag left them.

`"dk"` is the **third** caller of the same sub-record merge engine `"ms"` and `"vs"` already share; the only structural difference is that its address has one more part, so the namespace carries the collection (`dk:note:<nid>:text`). `formatVersion` **stays 3** — the D1 bump marks the desk format family and already covered this.

### The one real bug D2's tests found

**Double-clicking the paperclip mark silently did nothing.** `pointerdown` captures the pointer to the desk surface, which means every later event in the gesture — `pointerup` included — reports `target` as the surface rather than whatever is under the cursor. So `e.target.closest(".dclip-mark")` on release always said no. The answer is recorded on pointerdown now, while the question is still answerable. **This is the same class as the D1 glance's `pointerleave`, and worth stating as a rule: after `setPointerCapture`, `event.target` is a fact about the capture, not about the cursor. Anything a gesture needs to know about *where it started* must be captured at pointerdown.**

### Rules D2 adds

- **`deskObjects` is excluded from create-skeleton filling** in `fillCreateBlanks`, exactly as `milestones` and `viewState` are. Third appearance of one bug; a late `create` op for a project would otherwise assign an empty object over its clips.
- **A dangling reference is read, never repaired.** A card whose `clip` points at a clip that has been removed (or that this device hasn't received yet) simply renders loose. Repairing it would be a write, and a write triggered by rendering is how data drifts.
- **A cluster clamps as one object.** Clamping each member of a clip separately lets the card nearest the desk's edge stop while the others carry on, fanning the stack out against the boundary for good. `clampDelta()` holds the whole clip to the tightest constraint any member imposes.
- **Open/closed is per-device chrome, not content.** Which clip is fanned out lives in `viewLocal` beside `expanded`. It is not a field, not an op, and not synced.
- **The post-it tint is verified, not eyeballed.** `--desk-note-tint` is checked against `js/theme.js`'s own `contrast()` across the whole RGB cube in both themes; `--text-primary` and `--text-muted` clear AA on any project colour, `--text-faint` does not and is banned from a post-it.

### Round 2 (August 16, 2026, `dash-v42`)

Four bugs and three confirmed refinements. See `changes-2026-08-16-desk-d2-fixes.md`.

- **A post-it stopped losing its words.** "Emptying a post-it throws it away" had been built as "it is empty when it loses the cursor, so throw it away" — and a brand-new post-it is empty *by definition*. Anything that took the cursor away before the first keystroke tombstoned it, and the commonest is pressing on bare desk to pan. Renders are held for the life of that gesture, so the scrap stayed on screen looking alive while the words went into a dead record. **The rule now is the sentence it was always meant to be: you cannot empty something that was never filled.** A `noteTyped` map sits beside `noteDrafts` in `viewLocal` so a rebuild mid-word doesn't forget the answer, and Escape discards a blank never-typed scrap so an accidental double-click still costs one keystroke. As a backstop, committing words into a note that has been removed by any route un-tombstones it — never-delete means the record is there to bring back, and silently writing into a dead one is the same bug in a different coat.
- **The open grid is measured, not calculated.** A fixed 300px column pitch against cards that size themselves to CARD_MAX_W (410) guaranteed overlap. `openGrid()` now takes the members' real boxes and derives both pitch and column count; the view measures from the `_deskMount` hook, in the same task as the appendChild and before the browser paints, so the provisional layout is never seen. **General shape for this desk: anything that depends on how big something turned out to be is laid out at mount from real boxes, with the arithmetic staying in the DOM-free `js/desk.js`.**
- **An expanded card has its own z band** (`Z_EXPANDED`), set inline. Members of a clip all carry the *clip's* z, so DOM order alone decided who covered whom, and an expanded card in an open grid could be half-covered by a neighbour. It now leaves the argument entirely.
- **The stack is pinned from the RIGHT.** `stackSlot()`/`markSlot()` return a `right` coordinate and the view writes CSS `right` with `left: auto`. Not only a handedness preference: a card's width is its own business, so aligning *left* edges left the right edges ragged by up to 150px and the clip gripping nothing on the narrow sheets. The right edge is the only one that is the same for every member.
- **Two specificity bugs, one lesson.** The expanded card's `cursor: default` was beaten by `.dcard.is-clipped { cursor: grab }` (later, equal specificity), and the clip icon's quiet ink by `.on-ground .btn` (earlier, *higher* specificity). §14.19's round-5 bug was the same shape. **In this stylesheet, a rule meant to be an exception has to out-specify what it is excepting, not merely follow it** — hence `:not(.is-expanded)` on the clip-member rules and `.pb-acts .banner-clip` on the icon.
- **A selection cannot escape an expanded card.** `user-select: text` on the expanded card reopened §14.25's door by the side entrance: drag upward out of the card and the browser, finding nothing selectable between there and the top of the page, extends the selection into the banner. `user-select: contain` is Firefox-only, so the range is clamped on `selectionchange` instead — the one place on this desk where JS is the answer and CSS is not.
- **Unclipping now hands an attached post-it a real position** (and clears its `clip`), taken from where it is already sitting, so nothing appears to move. Without it a note created attached had no `pos` at all and fell back to the desk's origin corner.

## Key decisions still standing

- Dropbox over iCloud/Google Drive: Android compatibility + no recurring re-auth
- PWA + GitHub Pages: no native dev overhead, works across Mac/iPhone/iPad/Android
- All code delivered as uploadable zips or files with plain-English notes — no direct code access expected of Andra
- **Derived data is computed at render time and never written back.** A project's stage is worked out from the in-memory item every time the screen draws (`stageOf` in `js/milestones.js`). There is no stage field, no stage registry, and no op that writes one — so it cannot go stale, cannot conflict between devices, and cannot be edited into disagreement with the milestones it comes from. Any future "status that follows from other data" should follow this rule rather than adding a field
- **Milestones are sub-records, not items** — they can't be tagged, linked or attached to, on purpose. The escape hatch for the rare heavyweight case already exists: make a real item and link it to the project. Making them items would buy richness nobody asked for at the cost of every list and view needing a "not really an item" filter
- **Bulk edits introduce no new data.** A bulk action is the same single-item field edit run in a loop through the existing store methods (`addToSet`, `setField`, `assignToProject`). No batch records, no batch ops in the log, so sync and merge needed no changes at all. Any future "apply to many" feature should follow this rule
- **The sidebar is closed by default** (August 1, 2026) — "I almost never use it for what it's intended." A `☰ Filters` button in the topbar toggles it, remembered per device. **Settings and Read-aloud moved to the topbar first**, because they used to live at the bottom of the sidebar and hiding it would have stranded them — Settings is the only way to Dropbox, dark mode, text size and the device label. The tag/type/status filter list is untouched, just behind one tap; removing it outright was considered and rejected because filtering to a single tag has no other home
- **Views declare their own capabilities.** Select mode appears wherever a view module sets `supportsSelect: true`, rather than app.js hardcoding a list of view names — consistent with views-as-registered-modules
- **Select mode is a visible button, not a long-press.** Long-press is undiscoverable, fights text selection and dictation, and used to collide with kanban drag. It now collides with the row status control instead, which is why that control stands down in select mode — the reasoning survived the view it was written for
- **Unregister, don't delete.** Established with the corner cluster and reused for Kanban and Columns: take a feature out of the switcher but leave its feature files on disk when it may reasonably return. This is a maintainability choice for a nontechnical owner: restoration stays simple and does not require recovering code from Git history. Ordinary residue and abandoned implementation scraps do not get the same protection
- **Ember is still indicator-only; the PALETTE is what became decorative.** The August 2026 amendment permits the seven palette colours as filled grounds. It does not touch ember, and the distinction is load-bearing: ember means "past its date" and nothing else, everywhere, and it is not in the palette. Anything that would make ember decorative — or make a palette colour mean urgency — undoes this
- **A colour you pick is used exactly as picked.** Dash reports contrast and warns; it does not silently adjust. The only automatic decision is which of the two inks goes *on* a colour, which changes the writing rather than the colour. Chosen deliberately over auto-correction, and over refusing bad picks
- **Column widths are automatic, not draggable — and that was reasoned, not lazy.** Andra asked whether a dragged width would be remembered; it would (localStorage, per device, exactly like `dash.sidebar`). Persistence isn't the problem. **Saved widths go stale whenever the set of panels changes**, and adding widgets is the stated plan — so dragging would put "I want more widgets" and "I don't want to keep adjusting columns" in permanent conflict. Automatic layout self-heals when a panel is added, on every screen size. A panel that needs unusual room says so in its own module (`span: 2`), so the decision lives with the widget rather than in a saved layout that rots. **Nothing built blocks adding drag handles later** — the grid is token-driven and it would be additive
- **The rail is Home-only, on purpose.** It exists because capture must always be reachable. A rail that holds only readouts and navigation is not worth 340px and becomes an empty column the moment you scroll — which is what happened on the project page and why it was removed there. Judge any future rail by whether something must be *reachable*, not by symmetry with Home

## Operational notes for future sessions

- **The browser's HTTP cache sits in FRONT of the service worker, and it silently defeated three deploys.** Found August 1, 2026 while chasing the capture-box bug. GitHub Pages serves assets with `Cache-Control: max-age=600`, so for ten minutes after an upload the module loader can be handed a stale `app.js` from disk without the network or `sw.js` being consulted at all — "network-first" was a promise the worker could not keep. Proof, worth repeating if it's ever in doubt: fetch the same URL twice, once plainly and once with `{cache:"no-store"}`, and compare lengths. During this bug the server had 17,515 bytes and the running app had 17,034. **The practical damage is that a correct fix looks like a failed fix**, which is exactly what happened — two working fixes were reported as not working. `sw.js` now fetches with `cache: "no-store"` and precaches with `cache: "reload"` (v16). **After any upload, hard-reload once (Cmd+Shift+R) — a normal reload can still be served from the HTTP cache.** Before concluding a fix didn't work, verify what the browser is actually running
- **`due` and `remind` were written to `item.due` and read from `item.dates.due`.** Found August 1, 2026 the moment the Today panel needed them. They were declared as ordinary scalar fields, so `_applyOp`'s `it[op.field] = op.value` put them at the top level, while `emptyItem`, the query layer and the old Home panel all looked inside `dates`. The two never met. **Nobody had noticed because the editor had no date field at all** — there was no way to write one in the first place, which is also why "due dates don't show up" had been true since the beginning. Fixed with a `DATE_SCALARS` set that routes those two into `it.dates`; the op on the wire is unchanged (`{ field: "due" }`), so old logs, LWW bookkeeping and merge are untouched. **The lesson worth keeping: a field existing in the data model is not evidence anything can produce it.** When a surface is built for data, check something actually writes that data
- **An edit could arrive before the thing it edits was created, and the creation was thrown away.** Found August 1, 2026 by the Phase M1 out-of-order replay tests. Each device's log is read independently, so a `set` for an item can land before that item's `create` — `_ensure()` would conjure a blank to hold the edit, and the real `create` was then skipped by its own `if (!this.items.has(id))` guard. The entry kept the blank's empty title and default type permanently. Fixed with the same blank-filling rule milestone `add` uses: a late `create` supplies only fields no later op has claimed, merges rather than replaces set fields, takes the max of the date stamps, and never resurrects a tombstone. Tracked by `_fieldTs.__create` so a genuinely repeated create is still a no-op. **This class of bug is invisible in normal use** — it needs a specific arrival order — which is exactly why the replay-every-permutation test exists
- **The "newer format" guard no longer throws.** It used to stop with an error, which meant that the moment one updated device wrote a v2 snapshot, every not-yet-updated device was stuck until it refreshed. The addendum (§4.3) requires brief version skew to be survivable, and it is: logs are the source of truth and append-only, unknown op kinds are ignored-and-preserved, and unknown item fields ride through `Object.assign` untouched. It now sets `store.formatNotice` and app.js toasts it once. **The fix only helps forward** — a device on older code still throws, so every format bump needs "update all devices before editing" in its upload note
- **Format version lives in two places now.** `FORMAT_VERSION` in `store.js` stamps the snapshot header; `sync.js` also writes one `{"op":"header", formatVersion, device, at}` line per run at the top of that session's batch of log lines. Logs are append-only so they can't be re-headed retrospectively — per-run segment stamps are the honest equivalent, and they say which build produced which ops. `replayLog` skips `op: "header"` explicitly. `exportForSync()` had `formatVersion: 1` hardcoded and now reads the constant; check for that kind of literal on any future bump
- **`sw.js` no longer has a manual version-bump deployment step.** It uses one permanent `dash-runtime` cache. Same-origin GETs are network-first with `cache: "no-store"`; successful responses replace their cached copies, and offline requests fall back to the last good copy. New or renamed app files do not require editing `sw.js` merely to deploy them — once Dash requests them successfully while online, they are cached automatically. `sw.js` itself is uploaded only when the service-worker logic is intentionally changed.
- **The forced update reload is now conditional (v39).** `sw.js` still calls `skipWaiting()` and `clients.claim()` unconditionally, so a new worker still seizes an open tab — but `index.html` no longer reloads the instant `controllerchange` fires. It reloads immediately only if there has been no `pointerdown` or `keydown` yet; after a real interaction it records that an update is waiting and reloads when the tab is next hidden. **Measured, not assumed: `controllerchange` lands about two seconds after the page is on screen**, so the old unconditional reload had a two-second window in which it could throw away a navigation the person had just made. Anything that wants to force a reload from now on has to answer "is the person mid-something" first
- **`SHELL` is now an install-time precache list, not the deployment contract.** It is useful for the core files that should be immediately available offline when the service worker installs, but ordinary new modules can be cached at runtime after their first successful online request. A missing new file in `SHELL` is therefore no longer the classic "uploaded it and nothing happened" failure mode.
- **`js/views/home.js` and `js/views/shared.js` are now coupled** — home imports `renderPanel` from shared. Uploading one without the other breaks Home. In practice this is a non-issue because deployment drags whole folders, but it's the first real cross-file dependency between views and worth knowing when debugging a half-broken deploy
- **`--ember` and `--ember-default` must be kept equal in `tokens.css`.** The second one exists because `setAccent()` writes `--ember` as an *inline style* on `:root`, which beats the stylesheet — so "what is ember when nobody has picked anything?" cannot be answered by reading `--ember` back; it hands you the custom accent instead. `--ember-default` is never written by the accent flow, which is what makes it the honest answer, and it flips per theme so resetting in dark mode offers dark's ember. Added August 2026 in the code-health pass
- **All contrast maths lives in `js/theme.js`.** `luminance`, `contrast`, `inkFor`, `colorReport`, `resolveHex`, `tokenHex`. Settings, the item editor and every colour block need the same answers, and there must be exactly one definition of "is this readable". It reads token values off the live computed style, so it works against whatever theme is active — including one loaded from a JSON file. **The pure functions are testable headlessly** by stubbing `document`, `localStorage` and `getComputedStyle`; that's how the palette-as-ground numbers were verified before the rule was changed
- **`--tap-min` vs `--control-min` is a distinction to preserve.** `--tap-min` (44px) is the accessibility promise and must not be made conditional. `--control-min` is what components size to, and only *it* drops under `@media (pointer: fine)`. If a control ever needs to stay finger-sized regardless of pointer, point it back at `--tap-min` explicitly. Known edge: a touchscreen laptop reports its trackpad as the primary pointer and gets the smaller controls; everything stays above the 24px desktop floor, so it's a comfort question rather than a reachability one
- **There is one `!important` in `app.css`, and it is load-bearing.** `.today-band-overdue .mk` — type and status marks carry an **inline** colour from the registry (`typeChip` in `views/shared.js`), and inline styles can't be overridden any other way. A registry green on an ember ground is unreadable, so on that block the block owns the ink. Don't "clean it up"
- **`color-mix()` is used for hairlines, washes and textures on colour blocks.** It's computed from a token (`--ground-ink` / `--ember-ink` / `--text-on-accent`), never a literal, so it re-themes for free — this is the sanctioned way to get "a fainter version of the current ink" without inventing a token per opacity. Baseline in Safari/Chrome since 2023
- **Layout changes get checked in `mockups/home-panels-preview.html` before upload, not after.** There is no way to run Dash locally in this working setup, and a deploy-to-check loop is slow and risks a broken live app. The preview links the real CSS, so a layout that looks right there looks right in the app. **It cannot show touch sizing** — a Mac reports a trackpad, so the preview always renders the 28px controls; 44px behaviour has to be verified on the phone after uploading
- **Historical service-worker bug:** `js/views/home.js` was once missing from the old `SHELL` contract and a cold offline start exposed it. That incident is why offline behavior still gets checked when a new view is introduced, even though the current worker runtime-caches requested modules and no longer requires a manual cache-version bump
- **Ambient widgets get data through `store.onAction()`**, a listener channel that writes nothing — no op, no log line, no sync. It fires only on **local** edits, so a background sync landing never triggers a reaction. Listener exceptions are swallowed: a decorative widget must never be able to break an edit. Any future ambient/decorative feature should use this channel rather than inventing a new field
- **All four cluster widgets share one motion file.** Spring constants, breath period, ripple timing and the burst-coalescing window live in `js/widgets/motion.js`. Retuning the feel happens there, once, for all four — do not hardcode timings inside a widget
- **The pet is drawn in `--text-primary`, never `--ember`.** tokens.css reserves ember as an indicator only (overdue, stale, sync trouble) and explicitly not decoration. Near-black is a *material* in the specimen-archive system, which is what a cut-paper character is. This inverts correctly on the dark theme for free
- **`shapes.js` uses 48 outline points, and the number is load-bearing.** The six-lobed `burst` has features every 30°; 48 points divides the circle into 7.5° steps so every point and notch is sampled exactly. At 34 points the notches fell between samples and the shape rendered as a lumpy circle. Do not lower this without re-checking `burst`
- **Anything that repeatedly scans `store.all()` must be coalesced to one pass per frame.** The pet's neglect check wasn't, and a 30-item bulk edit meant 30 full archive scans. Same failure mode as the render loop, same fix. Assume any new subscriber to the store has this bug until it's been checked. **This rule was being broken by `app.js` itself until August 1, 2026** — the index rail was rebuilt on every redraw with one archive walk per type, per status and per tag (~28 in total), on every view including the ones with no rail. Fixed in the code-health pass; the lesson is that the rule applies to the app's own chrome and not only to widgets and views. **`js/entries.js` is the model to copy**: `collect()` takes a `want` argument and produces the dated entries and the unscheduled ones from a single walk, rather than offering two functions that each scan
- **A field inside a re-rendered view must not commit on every keystroke.** The milestone name boxes commit on Enter and on blur only, so typing emits no store change and therefore triggers no re-render mid-word; what's typed is also held in a per-`mid` draft on `ctx.viewLocal` so a background sync landing can't swallow it, and focus plus cursor position are restored on the next frame with `preventScroll`. This is the capture box's rule applied to a field that lives *inside* the render tree rather than outside it. **Any future in-view text field needs the same three parts** — deferred commit, a draft, and focus restore — not just one of them
- **Merge rules get headless replay tests before delivery, in every permutation.** A merge bug is silent: it doesn't throw, it just quietly has less in it. The pattern used for M1: hand-written multi-device log fixtures replayed in every possible order, asserting a byte-identical snapshot each time (with object key order normalised, since that isn't semantic), plus two live `Store` instances swapping real log lines. Two real bugs came out of it — the out-of-order create above, and a milestone ordering inconsistency. **Fixture timestamps must be realistic wall-clock milliseconds**; tiny fake epochs (`wall: 1000` = January 1970) sit before every item's own created date and make a converged state look divergent for reasons that can't happen in life
- **Procedurally-drawn widgets get headless frame tests before delivery.** Physics and generated geometry fail as a blank rectangle, not as an error message, so "it looked fine" is not evidence. The pattern used for the pet: stub the DOM and canvas, drive a fake clock through ~1,500 frames per scenario, and assert no NaN or Infinity ever reaches a canvas call. That method caught two real bugs (a lobed shape losing its notches; the un-coalesced archive scan). Worth repeating for the tide wave and the train
- **A sync poll must not redraw the screen when nothing changed.** Fixed August 1, 2026. `pullDropbox()` called `store.loadSnapshot()` on every 10-second poll regardless of whether the remote snapshot had changed, and `loadSnapshot()` ends in `_emit()` — so the whole UI was being rebuilt every 10 seconds, forever. Symptom was the Home capture box going dead mid-sentence. Both poll paths (Dropbox and folder) now compare the snapshot against `sync._lastSnapText` and skip the load if identical. Secondary benefit: re-applying an older remote snapshot over locally-edited items could undo them, and that window is now closed. **Any new polling code must not emit on a no-op**
- **The capture box owns its own focus, by rule rather than by patch.** August 1, 2026, after the blur guard below turned out to be necessary but not sufficient — the box still went dead, including on mouse movement, and the remaining thieves weren't worth enumerating. The rule now: focus stays in the box until it is *handed over* to something interactive (`button, a[href], input, textarea, select, [contenteditable], [tabindex], [role="button"]`). A blur whose `relatedTarget` is null is never something a person did on purpose, so the box takes focus back on the next frame, cursor position included. Two deliberate exceptions, both important: it does not grab focus back when `document.hasFocus()` is false (switching apps/tabs), and it stands down when the node has been detached, because the render restore pass handles that case. `preventScroll: true` on every refocus so the page never jumps. **If another always-on field is added later, reuse this rule rather than re-deriving it**
- **Decorative widgets must not take focus from a field being typed in.** `cluster.js` calls `frame.focus()` on pointerdown (its `preventDefault()` suppresses the default focus, so it's done by hand). The pet sits ~150px from the capture box, so brushing it mid-sentence stopped the typing. It now skips the focus call when the active element is a text field. Keyboard access is unaffected — Tab isn't a pointerdown
- **Blur is not proof the user left the field.** `container.innerHTML = ""` detaches the focused element and Chrome fires `blur` on the way out. Home's capture box cleared its "was focused" flag in `onblur`, which defeated its own focus-restore pass — text survived the re-render, the cursor didn't. The guard is `if (document.contains(e.target))`. Cursor position is preserved too, via `viewLocal.captureSel`. Any field that has to survive a re-render needs the same guard
- **Renders are coalesced to one per animation frame** (`scheduleRender` in `app.js`). Added July 31, 2026 because bulk actions emit one store change per item, and redrawing the whole screen dozens of times in a row locked the UI. Views needing an immediate redraw still call `ctx.rerender()`
- **"Today" changes at midnight while the app is open.** Every grouping on the Home sheet is computed against it, so `watchDayRollover()` in `app.js` re-renders on `visibilitychange`, on window focus, and on a once-a-minute check that only fires when the calendar date has actually changed. A no-op minute costs one string comparison and redraws nothing. Any future date-derived surface inherits this for free by living in the normal render pass — but must not add its own timer
- **Per-device `localStorage` keys now in use** (none of these are synced, on purpose): `dash.groupBy`, `dash.collapsed`, `dash.theme`, `dash.textScale`, `dash.dark`, `dash.rail` (index rail open/closed on List/Board — replaced `dash.sidebar`, which is now abandoned in place and read by nothing), `dash.sortBy` (the catalog band's sort order), `dash.cluster.pos` (widget positions — dormant while the cluster is shelved), `dash.pet.streak`, `dash.pet.lastOpen`, `dash.mergeNotes` (this device's unread merge notes), `dash.mergeNotesResolved` (the keys of notes this device has dismissed, cleared or restored — tombstones, added v39, capped at 1000; **it is what stops a dismissed note coming back**, and it must never be cleared alongside `dash.mergeNotes`, because the two records exist precisely so that shortening one does not shorten the other). The rule they follow: UI arrangement and per-device nudges stay local; anything that is *content* goes in the synced log
  - **Two keys are abandoned in place and read by nothing:** `dash.sidebar` (the old drawer's open/closed state, superseded by `dash.rail`) and `dash.view` (written on every view switch until the code-health pass, but never read — Dash always opens on Home by design). Both may still be sitting in your devices' storage; neither does anything. If a future feature wants "remember the last view", **use a new key** rather than inheriting a stale value from `dash.view`, for the same reason `dash.rail` didn't reuse `dash.sidebar`
- Deployment uses GitHub's web uploader: upload exactly the complete files/folders named in the handoff, keep folder paths intact, commit, wait for the automatic **Check Dash** action to go green, then verify Dash while online. `sw.js` is **not** part of ordinary uploads anymore; include it only when its own logic changed. Full steps are in `docs/deploy-runbook.md`
